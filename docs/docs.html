Docs / Philosophy & Overview

Cade design and architecture

Abandoning lossy recursive self-summaries. Grounded in lossless event history, dynamic projections, zero-loss 95% context rollover, and durable memory across native TUI, CLI, and Web workbenches.

Core architecture

Mainstream autonomous coding agents frequently lose precise line numbers and stack traces through periodic recursive self-summarization, compounding hallucinations over time. Cade establishes three deterministic pillars built for real-world engineering:

Lossless History & Projections Pillar 1

Sessions persist as append-only event logs with dynamic projections. Snapshot pooling enables atomic file reverts and window rewinds without silent truncation.

95% Summary-Free Rollover Pillar 2

Automatically rolls over context at 95% capacity, inheriting core goals while purging intermediate tool outputs, preventing degradation from heuristic summaries.

On-Demand Memory Pillar 3

Costly findings live in workspace Markdown, searched with existing tools and checked against original history. Normal turns and resume do not load Memory.

Data flow and workflow

In Cade, every interaction flows through a single unified runtime kernel responsible for sandbox policy gating, tool concurrency partitioning, and atomic event append:

Core invariants

  • Determinism over Heuristics: Critical lifecycle decisions (rollover, policy gating, reverts) are governed by deterministic algorithms, never left to LLM hallucinations;
  • Sandbox Path Jailing: Strict path boundaries jail read/write operations to the workspace, with high-risk operations gated by HITL approvals;
  • Interface Parity: TUI, CLI, and Web share identical event models and toolsets, guaranteeing 100% behavioral parity.

Docs / Installation

Installation and prerequisites

Cade requires Python 3.12 or newer. We strongly recommend using the modern uv package manager for isolated global installations and instant execution.

System prerequisites

Before installing Cade, ensure your operating system meets the following prerequisites:

  • Python: Version 3.12.0 or higher;
  • Operating System: Linux (Ubuntu 20.04+, Debian 11+, Arch, Fedora), macOS 12+, or Windows 10/11 (WSL2 recommended);
  • Git: Required for repository context awareness and snapshot tracing;
  • Bubblewrap (Optional but Recommended): On Linux, install bubblewrap for containerized sandbox isolation (Ubuntu/Debian: sudo apt install bubblewrap).

Install with uv tool

uv tool install packages Cade into an isolated virtual environment and links the CLI binary into your PATH:

Bash 
# 从 GitHub 仓库安装全局工具
uv tool install --python 3.12 git+https://github.com/reddishJade/cade.git

# 验证安装与版本
cade --version

Install with pip

If you prefer standard pip, install inside a dedicated virtual environment:

Bash 
python3.12 -m venv ~/.venvs/cade
source ~/.venvs/cade/bin/activate
pip install git+https://github.com/reddishJade/cade.git

Install for development

If you plan to contribute to Cade or develop custom extensions:

Bash 
git clone https://github.com/reddishJade/cade.git
cd cade
uv venv --python 3.12
source .venv/bin/activate
uv pip install -e ".[dev]"

# 运行静态类型与单元测试验证
uv run ruff check src/
uv run pyright src/
uv run pytest src/cade/tests -q

Check installation

Run the diagnostic command to check local runtime health, provider credentials, and sandbox availability:

Bash 
cade config --check

Docs / Lossless History

History and dynamic projections

Rejecting destructive file overwrites and silent context truncation. Cade records full events into append-only immutable logs, backed by snapshot pooling for instant atomic reverts.

Risks of model-generated undo

In many existing coding assistants, undo is merely an extra prompt asking the LLM to revert previous changes. This approach has critical drawbacks:

  • Secondary Hallucinations: The model often generates slightly different code when attempting to undo, frequently breaking surrounding untouched code;
  • Token Waste: Generating revert code and explanations burns hundreds of unnecessary tokens;
  • Dirty State Residuals: Aborted file operations leave corrupted files on disk that break compilers and linters.

Snapshots and file restoration

Cade enforces deterministic physical certainty. Whenever the agent calls any write tool (e.g. replace_file_content, write_to_file):

  1. Pre-write Capture: The runtime automatically records the unmodified file bytes into an immutable snapshot pool before touching the disk. Newly created files are flagged for deletion upon undo;
  2. Atomic Write: Modifications are committed atomically to disk;
  3. Physical Revert (/undo): When triggering /undo, the system restores pristine bytes from the snapshot pool and unlinks new files in milliseconds;
  4. Window Pointer Rewind: The runtime rewinds the active event stream pointer, ensuring reverted turns never clutter future model contexts.

Docs / 95% Context Rollover

Context rollover without summaries

Eliminating compounding distortions from heuristic recursive summaries. Smoothly rolls over context at 95% capacity, inheriting task goals while pruning intermediate tool dumps.

Risks of recursive summarization

When context fills up, most AI tools prompt the LLM to summarize previous messages. In real-world software engineering, this causes catastrophic degradation:

  • Loss of Precision Coordinates: Exact line numbers, regex groups, and strict type signatures are lost in summaries, crippling subsequent patch accuracy;
  • Compounding Hallucinations: If the model makes a minor incorrect assumption during summarization, that assumption becomes ground truth in future windows, driving refactors further off track;
  • Latency & Cost Spikes: Generating multi-thousand token summaries introduces major latency and burns expensive generation quotas.

Rollover budgets and triggers

Cade applies a strict context budget monitor that recalculates total tokens before each inference cycle:

Formula 
CurrentRatio = (PromptTokens + SystemPromptTokens) / ModelContextWindowLimit

if CurrentRatio >= 0.95:
    trigger_context_rollover()

Rollover lifecycle

  1. Goal & Constraint Retention: The original user objective, current goal, and key constraints carry over completely;
  2. Intermediate Output Pruning: Bulky intermediate payloads (e.g. 800-line search dumps and directory scans) are purged from active view, retaining only operation statuses;
  3. History on Demand: The new window can use history tools to locate original evidence; rollover does not automatically save or load Memory;
  4. Seamless Window Handoff: The developer continues the conversation without interruption, while the LLM gains fresh token headspace.

Rollover configuration

Tune the rollover threshold in cade.config.json or ~/.cade/settings.json:

JSON 
{
  "agent": {
    "rollover_trigger_ratio": 0.95,  // 默认 95% 水位线触发换窗
    "reserve_tokens": 16384          // 预留给生成与工具调用的安全 Token 空间
  }
}

Docs / Durable Memory

On-demand memory

Keep a few costly, reusable workspace findings. Each Memory is an editable Markdown file in .cade/memory/.

Scope and responsibilities

Memory is scoped to the current workspace. Repository/Git/Tests establish current facts, Event History preserves history, NOTE.md holds task state, and Skills hold reusable methods.

Explicit saves and sources

save_memory(path, markdown, sources) validates explicit Session/entry references and writes atomically. Replacements require the full previous expected_content. The Host replaces only the marked source footer and does not parse the body; existing sources do not prove conclusions.

Memory initiates no model calls, background organization, or extra inference. The existing runtime governs the normal Agent loop after a tool result.

Read and verify on demand

Normal turns, resume, and rollover do not scan or load Memory. For explicit historical needs or costly repeated investigation, use existing bash with rg "timeout" .cade/memory, read a file, follow session_id + entry_id into original History, and check current code and validation results. Memory does not expand the default tool surface.

Exact History reads do not depend on the navigation cache. The default local store trusts its current physical location, ignoring old project_path after workspace moves or renames; shared or custom stores require the first log record's workspace binding. Cross-session around supports ancestor before only, without switching Session/head. Read evidence follows ContextPolicy; Git SHA does not capture an uncommitted workspace.

Inspect and edit

/memory only shows the directory. Users may edit or delete files in an editor; the Agent revises through save_memory, with no state machine, index, or background maintenance.

Docs / Execution Modes

Execution modes: Plan, Build, and Act

Configure safety boundaries and automation levels for different engineering stages. Switch instantly with a single command without restarting your session.

Mode permissions and tools

Cade strictly partitions file write access and shell execution across three operating modes:

Execution Mode Read Tools Write Tools Command Execution Target Use Cases & Safety Goals
Plan Mode Always Allowed Strictly Disabled Read-only Inspections Exploring large codebases, mapping dependencies, and producing plans with zero modification side-effects.
Build Mode (Default) Always Allowed Allowed (Snapshotted) Interactive HITL Prompt Standard development workflow. Agent drafts precision patches; developer approves risky operations.
Act Mode Always Allowed Automated Execution Whitelisted Auto-Run Automated test suite generation, bulk refactors, and rapid execution in trusted environments.

Approval and rules

In Build or Plan modes, the PermissionEngine evaluates security policies using findLast reverse matching:

  • Default Policy: All file writes display a concise diff and record snapshot checkpoints before disk write;
  • Sensitive Commands: Destruction commands (rm), environment mutations, and socket requests trigger mandatory confirmation;
  • Approval Controls: Press y to approve, n to reject with an optional feedback note sent back to the agent.

Press Shift+Tab while idle to cycle act → build → plan.

Switch modes

Terminal 
/mode plan   # 进入只读规划模式
/mode build  # 进入自动实施与验证模式
/mode act    # 进入人工审批模式（默认）
/mode   # 查看或交互式选择模式

Docs / Built-in Tools

Built-in tools and safety

Strictly partitioning read-only concurrency from serial write barriers. Every tool enforces type validation and path boundary checks.

Tool specifications

view_file Read

Views text or binary files with mandatory StartLine and EndLine window slicing (max 800 lines per call) to prevent context flooding.

replace_file_content Write

High-precision continuous chunk replacement. Requires exact unique match of TargetContent with indentation, capturing pre-edit snapshots.

write_to_file Write

Creates new files or fully overwrites existing ones. Requires explicit Overwrite: true when replacing files, preventing accidental data loss.

run_command Execute

Executes bash commands in a jailed workspace or Linux container sandbox. Dangerous patterns (e.g. rm -rf /) are blocked for mandatory approval.

search_web Search

Performs real-time web search for modern framework API updates, technical articles, and GitHub issue solutions.

read_url_content Scrape

Fetches external documentation URLs and converts HTML into clean, token-efficient Markdown representations.

Docs / Security

Permissions, security, and sandboxing

Defense-in-depth architecture protecting developer machines. Principle of least privilege, workspace path jailing, and audited credential redaction.

Security controls

Layer 1: Path Jailing Path Jail

Restricts the agent exclusively to the active repository workspace. Path traversal attempts (e.g. ../../etc/passwd) and sensitive targets (~/.ssh/) are hard-blocked.

Layer 2: Policy Gating PermissionEngine

Maintains fine-grained policy rules evaluating tool names, file patterns, and shell commands: auto-allow, auto-deny, or mandatory human confirmation.

Layer 3: Bubblewrap Sandbox Linux Sandbox

On Linux, agent shell commands run inside a lightweight bubblewrap sandbox: read-only host mount, network namespace isolation, and ephemeral scratch areas.

Layer 4: Redacted Audit Logs Audit Trail

All interactions persist to audit.jsonl. Credential patterns (API keys, passwords, bearer tokens) are automatically redacted before logging.

Configure security policies

Customize security and permission rules in cade.config.json or ~/.cade/settings.json:

JSON 
{
  "security": {
    "workspace_only": true,
    "allow_network_commands": false
  },
  "execution_modes": {
    "rules": {
      "build": [
        { "action": "run_command", "command": "rm", "effect": "deny" },
        { "action": "run_command", "command": "git", "subcommand": "push", "effect": "ask" }
      ]
    }
  }
}

Docs / Configuration

Configuration and environment variables

Supports hierarchical configuration across global (~/.cade/settings.json), project-level (cade.config.json), and local (.cade/settings.json) tiers with CLI and environment overrides.

Configuration precedence

When the same setting is defined in multiple locations, Cade resolves values in the following order of precedence:

  1. Explicit CLI Flags (e.g. cade --model gpt-6-sol);
  2. Environment Variables (e.g. DEEPSEEK_API_KEY, OPENAI_API_KEY, CADE_MODE);
  3. Local Workspace Configuration (<project_root>/.cade/settings.json);
  4. Project Configuration (<project_root>/cade.config.json);
  5. Global User Configuration (~/.cade/settings.json);
  6. Built-in Framework Defaults (Default model: gpt-5.6-luna, effort: high, mode: act).

JSON configuration example

Complete JSON Configuration 
{
  "default_provider": "openai-codex",
  "default_model": "gpt-5.6-luna",
  "default_reasoning_effort": "high",
  "provider": {
    "model_profiles": {
      "subagent": {"provider": "openai-codex", "model": "gpt-5.6-luna", "reasoning_effort": "high"},
      "fallback": {"provider": "openai-codex", "model": "gpt-5.6-luna", "reasoning_effort": "high"}
    }
  },
  "agent": {
    "rollover_trigger_ratio": 0.95,     // 95% 水位线触发无摘要平滑换窗
    "reserve_tokens": 16384,            // 预留生成安全空间
    "max_steps": 30,                    // 单个任务最大自主步数
    "tool_workers": 4,                  // 只读工具并发线程数
    "tool_timeout_seconds": 120.0       // 工具执行超时，单位为秒
  },
  "security": {
    "workspace_only": true              // 工作区严格路径隔离

Subagent orchestration

Deconstruct complex engineering tasks into isolated sub-tasks. Spawn autonomous subagents with clean context windows to protect the primary context budget.

When to delegate

Scanning dozens of files in a massive repository quickly exhausts context budgets with inspection noise. Delegating to specialized subagents solves this fundamentally:

  • Isolated Context Sandboxes: Subagents execute within independent loops, consuming their own fresh token budgets;
  • Synthesized Return Payloads: After extensive exploration, subagents return structured summaries, saving thousands of tokens for the parent agent;
  • Specialized Roles: Configure specialized subagents (researchers, test runners, reviewers) with distinct prompts and cost-efficient models.

Docs / Lifecycle Hooks

Lifecycle hooks

Attach deterministic Python hooks at session bootstrap, before/after tool runs, and during inference cycles for linting, security gating, and telemetry.

Supported hook events

Hook Event Trigger Timing & Parameters Typical Use Cases & Action
on_session_start Triggered when a session is initialized or resumed. Receives session_id, cwd. Verify environment health, git sync check, clean up stale temporary files.
pre_tool_call Triggered right before executing a tool. Receives tool_name, arguments. Validate parameters and block sensitive file paths. Returning non-zero aborts tool execution.
post_tool_call Triggered immediately after a tool finishes. Receives tool_name, result. Auto-run ruff format after edits, execute linting, or run unit tests.
on_session_end Triggered when exiting Cade. Receives summary, event_count. Generate session report, notify team chat channels, clean sandbox containers.

Write a custom hook

Create a custom hook script at .cade/hooks/post_edit.py:

Python 
import subprocess, sys

def post_tool_call(tool_name: str, args: dict, result: dict):
    # 格式化写入工具修改的文件。
    if tool_name in ("replace_file_content", "write_to_file"):
        path = args.get("TargetFile")
        if path and path.endswith(".py"):
            subprocess.run(["ruff", "format", path], check=False)
            print(f"[Hook] Auto-formatted {path} via ruff")

Use the browser workspace to review streamed output, manage sessions, and respond to tool approval requests.

Startup and network configuration

Run cade web to start the local HTTP and WebSocket service. Use --open to open the browser:

Bash 
cade web                              # 默认绑定 127.0.0.1:8787
cade web --port 9000                  # 自定义监听端口
cade web --open                       # 启动服务并打开浏览器

Browser features

Multi-Session Drawer Session Drawer

Browse all historic engineering tasks, rename sessions, inspect token metrics, fork branches, and resume state seamlessly.

File changes Visual Diff

Review tool output and highlighted file changes in the event stream. Approval cards let you approve or deny pending operations.

WebSocket Event Stream Low Latency

The browser receives model output and tool events through a WebSocket connection.

Remote development through SSH

Keep the service bound to loopback. For remote access, forward the port through SSH. The web host has no built-in authentication:

Local Shell 
# 将远程服务端口转发到本机
ssh -N -L 8787:127.0.0.1:8787 user@remote-host

# 在本机浏览器打开 http://127.0.0.1:8787
