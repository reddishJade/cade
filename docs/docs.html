Docs / Philosophy & Overview

Cade design and architecture

Abandoning lossy recursive self-summaries. Grounded in lossless event history, dynamic projections, budgeted context rollover, and durable memory across native TUI, CLI, and Web workbenches.

Core architecture

Mainstream autonomous coding agents frequently lose precise line numbers and stack traces through periodic recursive self-summarization, compounding hallucinations over time. Cade establishes three deterministic pillars built for real-world engineering:

Lossless History & Projections Pillar 1

Sessions persist as append-only event logs with dynamic projections. Snapshots support per-file restoration; separate history commands change the active conversation branch.

Budgeted Context Rollover Pillar 2

Uses an input budget with a default ratio cap of 95% of the context window. Rollover retains task state and references to original history.

On-Demand Memory Pillar 3

Costly findings live in workspace Markdown, searched with existing tools and checked against original history. Each request includes a catalog of up to 4 KiB with paths, titles, and opening hints. Full bodies are read on demand.

Data flow and workflow

In Cade, every interaction flows through a single unified runtime kernel responsible for sandbox policy gating, tool concurrency partitioning, and atomic event append:

Core invariants

  • Determinism over Heuristics: Critical lifecycle decisions (rollover, policy gating, reverts) are governed by deterministic algorithms, never left to LLM hallucinations;
  • Sandbox Path Jailing: Strict path boundaries jail read/write operations to the workspace, with high-risk operations gated by HITL approvals;
  • Interface Parity: TUI, CLI, and Web share identical event models and toolsets, guaranteeing 100% behavioral parity.

Docs / Installation

Installation and prerequisites

Cade requires Python 3.12 or newer. We strongly recommend using the modern uv package manager for isolated global installations and instant execution.

System prerequisites

Before installing Cade, ensure your operating system meets the following prerequisites:

  • Python: Version 3.12.0 or higher;
  • Operating System: Linux (Ubuntu 20.04+, Debian 11+, Arch, Fedora), macOS 12+, or Windows 10/11 (WSL2 recommended);
  • Git: Required for repository context awareness and snapshot tracing;
  • Bubblewrap (Required by default on Linux): Install bubblewrap (Ubuntu/Debian: sudo apt install bubblewrap). Startup fails if it is missing. Linux bypasses bubblewrap only when security.sandbox.mode is danger-full-access and security.sandbox.network_access is allow.

Install with uv tool

uv tool install packages Cade into an isolated virtual environment and links the CLI binary into your PATH:

Bash 
# 从 GitHub 仓库安装全局工具
uv tool install --python 3.12 git+https://github.com/reddishJade/cade.git

# 检查 CLI 是否可用
cade --help

Install with pip

If you prefer standard pip, install inside a dedicated virtual environment:

Bash 
python3.12 -m venv ~/.venvs/cade
source ~/.venvs/cade/bin/activate
pip install git+https://github.com/reddishJade/cade.git

Install for development

If you plan to contribute to Cade or develop custom extensions:

Bash 
git clone https://github.com/reddishJade/cade.git
cd cade
uv venv --python 3.12
source .venv/bin/activate
uv pip install -e ".[dev]"

# 运行静态类型与单元测试验证
uv run ruff check src/
uv run pyright src/
uv run pytest src/cade/tests -q

Check installation

Check available commands, then inspect the configured authentication status:

Bash 
cade --help
cade auth status

  "default_model": "gpt-5.6-luna",
  "default_reasoning_effort": "high"

Bash 
cd /path/to/your/project

# 启动默认 TUI 工作台

# 启动终端工作台
cade tui

Docs / Lossless History

History and dynamic projections

Rejecting destructive file overwrites and silent context truncation. Cade records full events into append-only immutable logs, with host-managed snapshots for per-file restoration.

Risks of model-generated undo

In many existing coding assistants, undo is merely an extra prompt asking the LLM to revert previous changes. This approach has critical drawbacks:

  • Secondary Hallucinations: The model often generates slightly different code when attempting to undo, frequently breaking surrounding untouched code;
  • Token Waste: Generating revert code and explanations burns hundreds of unnecessary tokens;
  • Dirty State Residuals: Aborted file operations leave corrupted files on disk that break compilers and linters.

Snapshots and file restoration

The TUI captures workspace snapshots before and after each user task turn. Snapshot coverage depends on the host and excludes some paths, file types, and large files.

  • /undo [N] restores files from the most recent N undoable turns, defaulting to one. It checks conflicts and permissions per file and reports restored, skipped, and failed items. A turn can be partially restored.
  • /rewind [N] removes recent task turns from active conversation history and trims the snapshot index. It leaves workspace files unchanged.

See Sessions for snapshot coverage and restoration rules.

In Cade, conversation history is not a mutable array, but an append-only immutable event stream. The model prompt, TUI transcript, and Web views are purely deterministic projections derived from this stream:

Session branching with /fork

Thanks to lossless event logging, you can run /fork at any turn to create an independent exploration branch without corrupting the parent timeline, ideal for testing alternative architectural approaches.

Docs / Context Rollover

Context rollover without summaries

Eliminating compounding distortions from heuristic recursive summaries. Uses an effective input budget and predicted usage, with a default ratio cap of 95% of the physical window.

Risks of recursive summarization

When context fills up, most AI tools prompt the LLM to summarize previous messages. In real-world software engineering, this causes catastrophic degradation:

  • Loss of Precision Coordinates: Exact line numbers, regex groups, and strict type signatures are lost in summaries, crippling subsequent patch accuracy;
  • Compounding Hallucinations: If the model makes a minor incorrect assumption during summarization, that assumption becomes ground truth in future windows, driving refactors further off track;
  • Latency & Cost Spikes: Generating multi-thousand token summaries introduces major latency and burns expensive generation quotas.

Rollover budgets and triggers

The default agent.rollover_trigger_ratio of 0.95 caps the trigger at 95% of the physical window. Output reserve, safety headroom, an explicit token threshold, and the next-turn input allowance can cause earlier rollover.

The policy subtracts output reserve and headroom to calculate the input budget, caps the rotation threshold by the ratio and any positive explicit threshold, then subtracts the bounded next-turn input allowance to calculate the admission target. Predicted usage drives reclamation and rollover; the input budget is the hard send boundary. See the context policy for the algorithm, including unknown-window behavior.

Rollover lifecycle

  1. Goal & Constraint Retention: The original user objective, current goal, and key constraints carry over completely;
  2. Intermediate Output Pruning: Bulky intermediate payloads (e.g. 800-line search dumps and directory scans) are purged from active view, retaining only operation statuses;
  3. History on Demand: The new window can use history tools to locate original evidence; rollover regenerates the Memory catalog, with full bodies available on demand;
  4. Seamless Window Handoff: The developer continues the conversation without interruption, while the LLM gains fresh token headspace.

Rollover configuration

Tune the rollover threshold in cade.config.json or ~/.cade/settings.json:

JSON 
{
  "agent": {
    "rollover_trigger_ratio": 0.95,
    "reserve_tokens": 16384
  }
}

Docs / Durable Memory

On-demand memory

Keep a few costly, reusable workspace findings. Each Memory is an editable Markdown file in .cade/memory/.

Scope and responsibilities

Memory is scoped to the current workspace. Repository/Git/Tests establish current facts, Event History preserves history, NOTE.md holds task state, and Skills hold reusable methods.

Explicit saves and sources

save_memory(path, markdown, sources) validates explicit Session/entry references and writes atomically. Replacements require the full previous expected_content. The Host replaces only the marked source footer and does not parse the body; existing sources do not prove conclusions.

Memory initiates no model calls, background organization, or extra inference. The existing runtime governs the normal Agent loop after a tool result.

Read and verify on demand

Each provider request collects a Memory catalog of at most 4 KiB containing paths, first H1 titles, and opening paragraph hints. Recovery and rollover regenerate the catalog. Full bodies and source footers are read on demand. See Memory collection limits. For explicit historical needs or costly repeated investigation, use existing bash with rg "timeout" .cade/memory, read a file, follow session_id + entry_id into original History, and check current code and validation results. Memory does not expand the default tool surface.

Exact History reads do not depend on the navigation cache. The default local store trusts its current physical location, ignoring old project_path after workspace moves or renames; shared or custom stores require the first log record's workspace binding. Cross-session around supports ancestor before only, without switching Session/head. Read evidence follows ContextPolicy; Git SHA does not capture an uncommitted workspace.

Inspect and edit

/memory only shows the directory. Users may edit or delete files in an editor; the Agent revises through save_memory, with no state machine, index, or background maintenance.

Execution modes: Plan, Build, and Act

Configure safety boundaries and automation levels for different engineering stages. Switch instantly with a single command without restarting your session.

Mode permissions and tools

Cade strictly partitions file write access and shell execution across three operating modes:

Execution Mode Read Tools Write Tools Command Execution Target Use Cases & Safety Goals
Plan Mode Allowed within policy boundaries NOTE.md and plan notes under .cade/plans/*.md Read-only commands run directly; known mutations are blocked; unresolved effects go to the automatic reviewer Explore code and produce plan notes without changing project code.
Build Mode Allowed within policy boundaries Execute directly Read-only commands run directly; operations requiring review go to the automatic reviewer Implement and validate changes with automatic shell review.
Act Mode (Default) Allowed within policy boundaries User approval Read-only commands run directly; operations requiring review go to the user Review structured writes and shell mutations interactively.

Approval and rules

This table describes the default mode rules and security.approval_router="mode". Path restrictions, permission rules, grants, and explicit approval settings still apply. Setting the approval router to user or auto fixes the review route independently of the mode.

Press Shift+Tab while idle to cycle act → build → plan.

Docs / Built-in Tools

Built-in tools and safety

Strictly partitioning read-only concurrency from serial write barriers. Every tool enforces type validation and path boundary checks.

Tool specifications

read Read

Reads file content with path and optional offset and limit for pagination.

edit Write

Replaces old_text with new_text in path. Supports replace_all and rejects stale edits.

write Write

Creates or replaces a file using path and content.

bash Execute

Runs command with optional timeout_ms, workdir, and purpose. Permissions, review, and sandbox policy apply.

websearch Search

Searches with query; optional parameters include numResults, livecrawl, type, and timeout. Runs sequentially.

webfetch Scrape

Fetches url with optional format (markdown, text, or html) and timeout. Runs sequentially.

Parallel reads and serial write barriers

Only tools that declare parallel execution enter the read pool: read and optional grep, glob, find, and ls. Other tools run sequentially. The question tool takes a top-level questions array; each item has question and optional header, multiple, and options. See Tools and execution scheduling.

Docs / Security

Permissions, security, and sandboxing

Defense-in-depth architecture protecting developer machines. Principle of least privilege, workspace path jailing, and audited credential redaction.

Security controls

Layer 1: Path Jailing Path Jail

Restricts the agent exclusively to the active repository workspace. Path traversal attempts (e.g. ../../etc/passwd) and sensitive targets (~/.ssh/) are hard-blocked.

Layer 2: Policy Gating PermissionEngine

Maintains fine-grained policy rules evaluating tool names, file patterns, and shell commands: auto-allow, auto-deny, or mandatory human confirmation.

Layer 3: Bubblewrap Sandbox Linux Sandbox

On Linux, agent shell commands run inside a lightweight bubblewrap sandbox: read-only host mount, network namespace isolation, and ephemeral scratch areas.

Layer 4: Redacted Audit Logs Audit Trail

Additional tool audit logging is disabled by default (observability.audit_path is null). When enabled, audit input and output use pattern-based credential redaction. Session records and tool artifacts are saved separately and can contain raw content; this redaction does not make them safe to share. Review and sanitize them before sharing.

Configure security policies

Customize security and permission rules in cade.config.json or ~/.cade/settings.json:

JSON 
{
  "security": {
    "approval_policy": "on-request",
    "approval_router": "mode",
    "sandbox": {
      "mode": "workspace-write",
      "network_access": "deny"
    }
  },
  "execution_modes": {
    "default_mode": "act"
  }
}

Docs / Configuration

Configuration and environment variables

Supports hierarchical configuration across global (~/.cade/settings.json), project-level (cade.config.json), and local (.cade/settings.json) tiers with CLI and environment overrides.

Configuration precedence

When the same setting is defined in multiple locations, Cade resolves values in the following order of precedence:

  1. Global user settings: ~/.cade/settings.json.
  2. Project settings: cade.config.json, replaced by the file selected with cade --config PATH.
  3. Local workspace settings: .cade/settings.json.
  4. CADE_APPROVAL_POLICY overrides security.approval_policy.

Later explicit fields override earlier values. Nested objects merge recursively; arrays are replaced. Omitted fields use built-in defaults. API key environment variables supply credentials separately. Use cade exec --model provider/model for a temporary exec model override or /model in the TUI. See Configuration.

JSON configuration example

JSON configuration overrides 
{
  "default_provider": "openai-codex",
  "default_model": "gpt-5.6-luna",
  "default_reasoning_effort": "high",
  "provider": {
    "model_profiles": {
      "subagent": {"provider": "openai-codex", "model": "gpt-5.6-luna", "reasoning_effort": "high"}
    }
  },
  "agent": {
    "rollover_trigger_ratio": 0.95,
    "reserve_tokens": 16384,
    "max_steps": 30,
    "tool_workers": 4,
    "tool_timeout_seconds": 120.0
  },
  "security": {
    "sandbox": {
      "mode": "workspace-write",
      "network_access": "deny"
    }
  },

Model Context Protocol (MCP) integration

Seamlessly integrate with the open Model Context Protocol ecosystem, mounting databases, issue trackers, and third-party services directly into Cade.

MCP architecture and transports

Cade launches MCP servers as subprocesses and communicates through stdio. Upon startup, it performs automatic capability discovery and injects schemas dynamically:

Configure .cade/mcp_config.json

JSON 
{
  "mcpServers": {
    "sqlite": {
      "command": "uvx",
      "args": ["mcp-server-sqlite", "--db-path", "./data/app.db"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxxxxxxxxxxxxx" }
    }
  }
}

Use MCP tools in sessions

Restart Cade after changing MCP configuration. Use /mcp [status] to inspect connectivity; live reload is not supported. Run /tool list to view registered tools under mcp__<server>__<tool> namespaces. Prompt the agent naturally to utilize them:

Prompt

Skills and domain instructions

Encapsulate domain-specific engineering guidelines, complex refactoring protocols, and test rules into modular SKILL packages reusable across teams.

Skill directory layout

Cade discovers user skills in ~/.cade/skills/ and ~/.agents/skills/. Project directories .cade/skills/ and .agents/skills/ are included only when skills.trust_project_skills is true (default: false). An explicit paths.skills_dir is trusted and has highest priority:

Directory Tree 
.cade/skills/
└── refactor-clean-code/
    ├── SKILL.md          # 必须：主规范说明与 YAML 元数据
    ├── examples/         # 可选：优秀与错误代码范式对照
    └── checklists/       # 可选：重构验收检查清单

Write a SKILL.md file

SKILL.md Template 
---
name: refactor-clean-code
description: Specialized engineering guidelines for module decoupling and unit tests.
---

# Core Refactoring Invariants
1. Functions must not exceed 40 lines; modules must not exceed 300 lines;
2. All function parameters and return types must have explicit type annotations;
3. Always execute `pytest tests/` via bash to verify zero regressions;
4. Enforce strict I/O separation; never issue network requests within domain entities.

Skill commands

  • /skill NAME [prompt]: Activate a discovered skill. An optional prompt becomes a follow-up task.
  • Discovered skill summaries appear in the system prompt. The model can load full instructions through the internal skill tool when the task matches.

Docs / Subagents

Subagent orchestration

Deconstruct complex engineering tasks into isolated sub-tasks. Spawn autonomous subagents with clean context windows to protect the primary context budget.

When to delegate

Scanning dozens of files in a massive repository quickly exhausts context budgets with inspection noise. Delegating to specialized subagents solves this fundamentally:

  • Isolated Context Sandboxes: Subagents execute within independent loops, consuming their own fresh token budgets;
  • Synthesized Return Payloads: After extensive exploration, subagents return structured summaries, saving thousands of tokens for the parent agent;
  • Specialized Roles: Configure specialized subagents (researchers, test runners, reviewers) with distinct prompts and cost-efficient models.

Docs / Lifecycle Hooks

Lifecycle hooks

Run configured external commands for tool constraints and lifecycle notifications. Commands exchange JSON through stdin and stdout.

Supported hook events

  • pre_tool: A synchronous constraint hook before tool execution.
  • post_tool: A background notification after a tool returns.
  • before_agent_start: A background notification before a user instruction runs.
  • before_provider_request: A background notification after request assembly.
  • on_context_window_reset: A background notification during context rollover.
  • on_error: A background error notification.

Configure a hook

Add a hook entry to cade.config.json. Commands are nonempty argv arrays and run directly without a shell. Each command receives a redacted JSON object on stdin with event, tool, input, output, error, metadata, and correlation IDs. Stdout must be empty or a JSON object; send diagnostic text to stderr.

JSON 
{
  "hooks": {
    "entries": [
      {
        "event": "post_tool",
        "matcher": "edit",
        "command": ["python3", ".cade/hooks/post_edit.py"],
        "failure_policy": "warn"
      }
    ]
  }
}

Create .cade/hooks/post_edit.py:

Python 
import json
import sys

record = json.load(sys.stdin)
print(f"Tool finished: {record['tool']}", file=sys.stderr)
print("{}")

A synchronous pre_tool hook can return decision (allow, ask, or deny) and an arguments object. Its decision can only tighten permissions. failure_policy="fail" raises an error to its caller and stops the tool attempt. The other configured events run through a background queue: exceptions are logged and do not propagate to the active tool or instruction. See Lifecycle hooks for failure policies and /hooks for diagnostics.

Docs / TUI & exec

TUI and exec

TUI provides terminal interaction; exec provides automation. Both share sessions, permissions, and runtime events.

Launching the terminal workbench

Bash 
cade tui                  # 进入终端工作台
cade exec --approval never --model deepseek/deepseek-flash "Review the current project" # 指定初始模型启动

Input syntax and shortcuts

The CLI interface provides powerful input prefixes for daily speed:

  • @ File Ingestion: Mentioning @src/cade/main.py reads and embeds file bytes directly into prompt context;
  • ! Raw Shell Escape: Starting with an exclamation mark (e.g. !git status) executes commands directly on host without consuming LLM tokens;
  • / Slash Commands: Execute /undo, /mode plan, /mode act directly;
  • Multi-line input: Ctrl+J inserts a new line. Alt+Enter inserts a new line while idle and steers an active run; Shift+Enter support depends on the terminal.

Noninteractive execution and pipelines

Use cade exec for noninteractive runs. A positional prompt does not consume stdin; use --prompt-file - to read the complete prompt from stdin. These examples use --approval never to deny approval requests without requiring a TTY:

Shell Pipeline 
# 单次问答输出结果并退出
cade exec --approval never "Analyze dependencies in pyproject.toml and produce a markdown report"

Docs / Web Workbench

Browser workspace

Use the browser workspace to review streamed output, manage sessions, and respond to tool approval requests.

Startup and network configuration

Run cade web to start the local HTTP and WebSocket service. Use --open to open the browser:

Bash 
cade web                              # 默认绑定 127.0.0.1:8787
cade web --port 9000                  # 自定义监听端口
cade web --open                       # 启动服务并打开浏览器

Browser features

Multi-Session Drawer Session Drawer

Browse all historic engineering tasks, rename sessions, inspect token metrics, fork branches, and resume state seamlessly.

File changes Visual Diff

Review tool output and highlighted file changes in the event stream. Approval cards let you approve or deny pending operations.

WebSocket Event Stream Low Latency

The browser receives model output and tool events through a WebSocket connection.

Remote development through SSH

Keep the service bound to loopback. For remote access, forward the port through SSH. The web host has no built-in authentication:

Local Shell 
# 将远程服务端口转发到本机
ssh -N -L 8787:127.0.0.1:8787 user@remote-host

# 在本机浏览器打开 http://127.0.0.1:8787
